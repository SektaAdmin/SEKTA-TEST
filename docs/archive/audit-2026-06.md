## 1. БД і грошова цілісність

### 1.1 🔴 `class_series`: RLS вимкнено + повний DML-грант для `anon`

- **Факт:** `pg_class.relrowsecurity = false` для `class_series`; гранти `INSERT, UPDATE, DELETE, SELECT`
  видані ролям `anon` І `authenticated` (звірено `aclexplode` живої БД). Security advisor: ERROR
  `rls_disabled_in_public`.
- **Ризик:** anon-ключ публічний (лежить у браузер-бандлі). Будь-хто без логіну може через
  `POST /rest/v1/class_series` переписати або **видалити всі шаблони тижня** (і `series_clients`?
  ні — там RLS з 2 політиками тримає; але сам `class_series` відкритий повністю). Це не гроші,
  але знищення розкладу-шаблону + бруд у `generate_week`.
- CLAUDE.md документує виняток («class_series — RLS вимкнено»), але не фіксує наслідок «anon може писати».
- **Рекомендація:** `ENABLE ROW LEVEL SECURITY` + `owner_admin_all` (+ за потреби trainer/client SELECT),
  або мінімум `REVOKE ALL ON class_series FROM anon`. Одна міграція, шаблон політик уже є.

### 1.2 🔴 `update_training_type_sort_orders`: SECURITY DEFINER без гейта, EXECUTE у PUBLIC

- **Факт:** тіло функції (звірено з БД) — голий цикл `UPDATE training_types SET sort_order` **без жодної
  перевірки ролі**; EXECUTE не відкликано від PUBLIC → advisor підтверджує: «can be executed by the `anon`
  role». DEFINER оминає RLS.
- **Ризик:** анонім або залогінений client/trainer переписує порядок довідника. Збиток дрібний
  (лише `sort_order`), але це пряме порушення моделі «admin не редагує `training_types`» (інв. #9)
  і єдина DEFINER-RPC без гейта — патерн `can_manage_enrollment`-харденінгу її не покрив.
- **Рекомендація:** додати staff-гейт усередину (`auth_role() IN ('owner','admin')` — owner-only за
  матрицею) + `REVOKE ... FROM PUBLIC, anon`.

### 1.3 🟠 PUBLIC EXECUTE на грошових RPC (захист — лише непрямий, через RLS)

- **Факт (живі гранти):** `create_sale`, `update_sale`, `delete_sale`, `update_client_balance`,
  `auto_close_classes` мають EXECUTE у PUBLIC; `generate_week` — явний грант `anon` + PUBLIC.
  Усі вони SECURITY INVOKER, тож реальна спроба anon/client впирається в RLS таблиць
  (у anon політик немає, у client немає write-політик на `sales`/`clients`) — **зараз не експлуатується**.
- **Ризик:** захист тримається на одному шарі (RLS), а не на двох, як в enrollment-RPC після
  харденінгу (`mark_attendance` — EXECUTE лише `postgres` ✅ звірено). Будь-яка майбутня
  «тимчасова» політика для client/trainer на `sales`/`clients` мовчки відкриє грошові RPC.
- **Рекомендація:** `REVOKE ... FROM PUBLIC, anon` для всіх перелічених (та `EXECUTE → authenticated`
  лише де треба) — дзеркало міграції `harden_enrollment_rpc_anon_and_public_grant`.

### 1.4 🟠 RPC без `SET search_path = public, pg_temp` (порушення інв. #10)

- **Факт (`pg_proc.proconfig` живої БД + advisor):** без search_path лишилися
  **`create_sale`**, **`update_sale`** (грошові!), `generate_week`, **`check_class_capacity`**
  (тригер-функція enrollments!), `check_class_conflicts`, `check_client_conflict`,
  `calc_trainer_salary`, `calc_trainer_salary_v2`, `set_updated_at`.
- **Ризик:** вектор ескалації через підміну search_path; для тригера `check_class_capacity` —
  виконується при кожному INSERT enrollment.
- **Рекомендація:** одна міграція `ALTER FUNCTION ... SET search_path = public, pg_temp` на всі дев'ять.

### 1.5 🟠 PUBLIC-грант на DEFINER-RPC з внутрішніми гейтами

- **Факт:** `get_session_balance_after`, `get_session_debtors_for_date` — SECURITY DEFINER з PUBLIC-грантом,
  але **всередині є гейти** (`auth_role()`-перевірки, читано тіла) → PII не витікає (anon має дефолт-роль
  `client` і падає на `current_client_id()`/`access denied`).
- **Ризик:** низький, але advisor шумить, і грант ширший за потрібний.
- **Рекомендація:** включити в ту ж revoke-міграцію, що й 1.3.
