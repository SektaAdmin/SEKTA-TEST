# Аудит сценаріїв: особистий кабінет клієнта

**Дата:** 2026-06-16  
**Зона:** `/app/client/**`, `lib/queries/client-cabinet*.ts`, RPC `client_enroll` / `client_cancel`  
**Метод:** читання коду + прямий запит RLS-політик і тіл RPC через Supabase MCP

---

## Структура кабінету

| Екран | Route | Дії клієнта |
|-------|-------|-------------|
| Головна / меню | `/client` | перегляд профілю, навігація, вихід |
| Розклад / самозапис | `/client/schedule` | перегляд занять, фільтр тренером/днем, запис, підтвердження |
| Мої візити | `/client/visits` | перегляд майбутніх і минулих записів з фільтром по дню |
| Деталі запису | `/client/visits/[id]` | перегляд деталей, скасування, Google Calendar |
| Абонементи | `/client/subscriptions` | перегляд депозиту, залишків занять, історії покупок |

### RLS-матриця (роль client)

| Таблиця | Дозволи |
|---------|---------|
| `clients` | SELECT WHERE `id = current_client_id()` |
| `client_contacts` | SELECT WHERE `client_id = current_client_id()` |
| `client_session_balances` | SELECT WHERE `client_id = current_client_id()` |
| `enrollments` | SELECT WHERE `client_id = current_client_id()` |
| `classes` | SELECT всі (без фільтра — весь розклад) |
| `halls`, `tickets`, `training_types` | SELECT всі |
| `trainers` | SELECT всі |
| `sales` | SELECT WHERE `client_id = current_client_id()` |
| `balance_transactions` | SELECT WHERE `client_id = current_client_id()` |
| Всі інші | немає доступу |

Прямі INSERT/UPDATE/DELETE заборонені на всіх таблицях. Мутації — тільки через SECURITY DEFINER RPC.

### RPC доступні для клієнта

| RPC | Безпека | Доступ |
|-----|---------|--------|
| `client_enroll` | SECURITY DEFINER | authenticated |
| `client_cancel` | SECURITY DEFINER | authenticated |
| `get_session_balances_running` | SECURITY DEFINER | authenticated (client-gated) |
| `class_availability` | SECURITY DEFINER | authenticated |
| `cancellation_deadline` | INVOKER | public |

## Знайдені потенційні проблеми

### MEDIUM

**[S06] `client_enroll` RPC — перевірка балансу не враховує вартість 2-год заняття**

Файл: RPC `client_enroll` (PostgreSQL)

RPC перевіряє `COALESCE(v_balance, 0) <= 0` — тобто вимагає хоча б 1 сесію незалежно від вартості. Для заняття `duration_min >= 120` вартість = 2 сесії, але при balance=1 RPC дозволить запис. `auto_close` потім спише 2 сесії → balance = -1.

UI захищений (перевіряє `availableByType >= cost`), але пряме API-звернення може обійти це. Не є security-проблемою (клієнт шкодить тільки собі), але порушує задекларований інваріант «не в мінус».

Де виправляти: у тілі `client_enroll` замінити `<= 0` на `< v_cost`, де `v_cost = CASE WHEN v_class.duration_min >= 120 THEN 2 ELSE 1 END`.

---

**[S11] Заповненість занять (`availability`) в `/client/schedule` — тільки SSR, не оновлюється на клієнті**

Файл: [app/client/schedule/page.tsx](app/client/schedule/page.tsx) + [app/client/schedule/ClientSchedule.tsx](app/client/schedule/ClientSchedule.tsx)

`availability` — пропс від SSR, не перезавантажується через `useAsync`/`useListQuery`. `classes` оновлюється через `refetchOnVisible`, але `availability` — ні.

Наслідок: якщо між завантаженням сторінки і кліком «Записатись» слоти заповнилися — модалка показує «Підтвердити запис?» замість «У резерв?», клієнт натискає «Записатись» і потрапляє в чергу з несподіваним результатом.

Сервер коректний (advisory lock + RPC повертає реальний статус), і toast покаже «У черзі». Але це сюрприз для клієнта.

### LOW

**[D08] Модалка скасування для `waitlist`-записів показує хибне попередження про штраф**

Файл: [app/client/visits/[id]/VisitDetail.tsx](app/client/visits/[id]/VisitDetail.tsx), рядок ~66

`isFreeCancellation` рахується від `starts_at`. Для `waitlist`-запису після дедлайну модалка показує «⚠️ Буде списано N год», але `client_cancel` → `change_enrollment_status` при `sessions_used=0` завжди поверне `charged=false`.

Клієнт може злякатися попередження і не скасувати місце в черзі.

Де виправляти: у `VisitDetail` при `enrollment.status === 'waitlist'` пропускати перевірку `isFreeCancellation` і завжди показувати «Скасування безкоштовне (ви в резерві)».

**[D12] Кнопка «Додати до Google-календаря» видима для waitlist-записів**

Файл: [app/client/visits/[id]/VisitDetail.tsx](app/client/visits/[id]/VisitDetail.tsx), рядок ~102

Умова показу кнопки: `!isPast && !c.is_cancelled && enrollment.status !== 'cancelled'`. `waitlist` проходить цю умову.

Клієнт у резерві може додати подію до календаря, але місця немає — він прийде і виявить, що зал повний.

Де виправляти: додати `enrollment.status !== 'waitlist'` до умови або показувати кнопку з приміткою «(якщо підтвердять місце)».
